Ideally, instructions to spawn entities occur in a predictable order

- Spawn entity (1)
- Spawn entity (2)

address of entity (1) < address of entity (2)

What if the instruction to spawn entity (2) comes in from the network before the
instruction to spawn entity (1). We delete the entity (2), spawn entity (1),
then spawn entity (2) again

- Spawn entity (2a)
- Rollback
    - Delete entity (2a)
- Spawn entity (1)
- Fastforward
    - Spawn entity (2b)

The consequence is that the address of (2a) != the address of (2b). In fact,
the address of entities in the pool is unpredictable.

There will be a system with a separate pool of references to entities. All of
these references are owned by the server. Entities in this pool are always
spawned by messages from the server.

Since the address of entity (2) may change, we cant have instructions that are
dependent on the address returned by the spawning instruction. If one instruction
spawns a bunch of instructions, they should all be independent. Dependent
instructions must be daisy-chained.

The instruction to allocate an entity must also spawn instructions to spawn each of
its components, so we have a lot of instructions allocating entities. This
functionality can be wrapped in a function call.


bbCoreSynchronous_spawnTestEntity(&core, &ECS, &entity, "Test Entity 2", bbInstructionSource_internal, null_handle);

This is interesting. This function returns an entity then sets up an undo instruction.
An instruction calls this function then launches other instructions to act on the entity.
If used carefully this should be OK. There is a lot of juggling bbInstruction_source(es).
Instructions involved will cause bugs if the bbInstruction_source is not what it should be.
Not that I have a clear idea of what the bbInstruction_source(es) should be.
For now, bbCoreSynchronous_spawnTestEntity must have bbInstructionSource_internal
